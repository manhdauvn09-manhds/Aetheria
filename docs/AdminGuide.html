🔒 Aetheria — Admin Guide

Moderation, enforcement, and system maintenance for Aetheria operators.

⚠️ Important: Admin tools are powerful and visible in audit logs. All actions are permanently recorded. Use responsibly.

1. Admin Access & Authentication

Who Can Access Admin?

  • Admins: Role-based access control. Admins are assigned via database directly (no self-signup).
  • Login: Via admin panel (separate from player login). Uses same JWT auth but admin-only procedures.
  • MFA: Recommended (not enforced, but strongly advised).
  • Session: 15-minute timeout for security. Manual logout required to clear session.

Accessing Admin Panel

Navigate to /admin endpoint (requires valid admin token). Login screen requests email + password.

2. Core Admin Tools

2.1. User Moderation (Ban / Unban)

⚠️ Caution: Bans are permanent until reversed. Always verify reason before executing.

Ban Reasons (recommended)

  • Toxicity in chat (slurs, harassment)
  • Cheating detected (anomalous match data, replay hash mismatch)

  • RMT (real-money trading) involvement
  • Exploit abuse (game-breaking glitch)
  • Spam / flooding

2.2. Item Grants (Economy Adjustment)

Manually grant items to a user (e.g., compensation for lost progress, event entry item).

Item IDChoose from item catalog (weapon, armor, consumable, etc.)

Example Use Cases

  • Bug Fix Revert: If player lost items due to glitch, manually restore stack.
✓ Safe: Item grants do not trigger immediate notifications to players. Check audit log later to verify completion.

3. Bulk Admin Operations

Scripted operations for server-wide events, maintenance, or seasonal resets.

3.1. Season Reset

  • PvP rank soft reset (keep 70% of MMR, reset tier to Bronze)
  • Leaderboard snapshot (archive top 100 players for season history)
  • Guild raid counter reset
  • Issue seasonal cosmetic to all participants in previous season

3.2. Emergency Compensation (Server Outage)

  • Grant 500 gold to all users who attempted login during downtime window (detected via audit logs)
  • Extend battle pass deadline by 24 hours
  • Double XP for next 6 hours (feature flag)

3.3. Scheduled Maintenance

  • Set global flag maintenance_mode = true
  • Broadcast message: "Patch in progress. Estimated 30 min."
  • Gracefully disconnect all players (auto-save triggered)
  • Deploy code changes
  • Set maintenance_mode = false
  • Players auto-reconnect with resume banner

4. Security & Best Practices

4.1. Audit Trail

✓ Every admin action is logged:
  • Who: Admin username
  • What: Action type (ban, grant, flag change)
  • When: Timestamp (UTC)
  • Why: Reason field (free text)
  • Result: Success/failure + affected entity ID

4.2. Approval Workflows (for critical actions)

Recommended process for high-impact decisions:

  1. Investigation: Audit log replay to confirm issue.
  2. Peer Review: Message another admin with findings.
  3. Action: Execute (with reason documented).
  4. Transparency: Post in #moderation channel (internal); affected player gets notification.

4.3. Password & Access Management

  • Admin passwords: strong (16+ chars, mixed case, symbols).
  • Rotate every 90 days.
  • Never share admin credentials. Each admin has unique login.
  • Session timeout: 15 min of inactivity → auto-logout.
  • Suspicious login (unusual IP/location): flag for verification.

4.4. Common Mistakes to Avoid

❌ Don't:
  • Ban without audit log evidence first.
  • Grant excessive items (economy inflation risk).
  • Leave feature flags in "broken" states overnight (e.g., pvp_enabled = false for debugging).
  • Share admin credentials. Use unique logins.
  • Forget to document reason for action (required in audit log).

5. Incident Response Protocol

5.1. Cheating Detection

  1. Alert Trigger: Anti-cheat system detects replay hash mismatch or anomalous action sequence.
  2. Investigation: Replay the match server-side. Confirm tampering.
  3. Decision: Ban or warn (first offense = warning + rank reset; repeat = permanent ban).
  4. Victim Comp: Revert rank loss for opponents; grant 100 gold.
  5. Log: Action recorded in audit trail + moderator dashboard.

5.2. Toxic Player Report

  1. Report Filed: Player clicks "Report" button in chat.
  2. Review: Admin checks chat log (profanity filter, context).
  3. Action: Verbal warning (cached msg: "Tone it down"), mute (24h), or ban (repeat offender).
  4. Appeal: Player can email support@aetheria.com; independent admin reviews.

5.3. Economy Exploit

  1. Symptom: Unusual spike in marketplace prices or item duplication.
  2. Root Cause: Check auction logs for pattern (e.g., user A lists item, user B instant-buys 100x, prices spike 10x).
  3. Fix: Revert affected transactions (delete orders, refund gold).
  4. Ban: Perpetrators banned; innocent users compensated.

6. Reporting & Analytics Dashboard

  • Daily Active Users (DAU): Trend chart over past 30 days.
  • PvP Queue Health: Match success rate, avg wait time.
  • Economy Health: Gold in circulation, item inflation index.
  • Crash/Error Rate: Top error messages, affected build versions.
  • Moderation Metrics: Bans this week, appeal resolution time.
  • Feature Usage: Shop usage rate, guild participation rate.

7. Security & Hardening (v1.1)

The platform underwent a 35-finding audit (SEO + frontend + backend) and two hardening passes. Operational notes admins should know:

7.1. Authentication & Sessions

  • Per-IP auth rate limit: 10 req / 60 s on auth.login / signup / refreshToken / requestPasswordReset / confirmPasswordReset / requestEmailVerification. Brute-force a 10k password dictionary now takes ~16 hours instead of ~100 minutes.
  • Argon2id: 19 MiB / t=2 / p=1 (OWASP 2024 baseline).
  • Refresh tokens: stored as httpOnly + SameSite=Strict cookies; rotated on every refresh; revoked on logout / password reset.
  • Access tokens: 15-min TTL with a jti claim. Realtime gateway tracks active JTIs and rejects a second concurrent WebSocket session for the same token.
  • JWT secret: bounded 32–512 bytes; validated at boot.

7.2. PII Handling

  • Audit payloads never contain raw email; redactEmail() masks the local-part to a***@domain. Junior staff querying audit_log cannot reconstruct full addresses.
  • Browser storage: only id / displayName / roles / oauthProvider are persisted to localStorage; email and access tokens stay in memory only.

7.3. HTTP / Browser Hardening

  • Content-Security-Policy + 5 headers (X-Frame-Options DENY, X-Content-Type-Options nosniff, Referrer-Policy strict-origin-when-cross-origin, Permissions-Policy lockdown, Strict-Transport-Security in prod).
  • tRPC errors strip stack in production; only the typed AppError envelope reaches clients.

7.4. Cron Audit Trail (B14)

Every destructive worker job now writes an audit_log row with actorUserId = NULL. To verify cron health, run:

SELECT action, target_type, payload, created_at
FROM audit_log
WHERE action LIKE 'cron.%'
ORDER BY created_at DESC LIMIT 50;

Expected actions: cron.dailyReset, cron.weeklyReset, cron.seasonReset.

7.5. Combat Integrity (B13)

The replay-hash check defeats client-side tampering by re-running the action_log against a fresh init and comparing hashes. File-level integrity (signed snapshot, OS-level monitoring) is out-of-scope — admins with file-system access are trusted by the threat model. Standard incident response (7.5.1) still applies for any operator action against the runs SQLite file.
